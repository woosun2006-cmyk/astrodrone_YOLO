## 원인분석

### 배경

PC(WSL) 한 대에서 Gazebo + SITL + YOLO 를 모두 돌리고, Jetson 의 실제 제어
스택(`mavlink_proxy` / `target_distance` / `hybrid_guidance`)이 그것을 소비하도록
연결하는 것이 목표였다.

`YOLO_MODEL/cpp/yolo_headless.cpp` 는 GStreamer 파이프라인이
`nvarguscamerasrc`(Jetson L4T Argus)로 하드코딩되어 있어 Gazebo 프레임을 읽을 수
없다. 기존 `gazeboSim/gazebo_camera_target.py` 는 HSV 색상 임계값이지 신경망이
아니므로, **시뮬레이션에서 YOLO 는 한 번도 돈 적이 없었다.**

### 관찰 1 — PC 에는 추론 런타임이 없다

PC(WSL Ubuntu)에 `torch` / `torchvision` / `ultralytics` / `onnxruntime` 이 모두
없다. 다만 apt 로 설치된 OpenCV 4.6.0 이 GStreamer 와 dnn 모듈을 함께 갖고 있어
`cv2.dnn.readNetFromONNX` 로 ONNX 를 직접 돌릴 수 있다. **추가 설치 없이 실제
가중치를 쓸 수 있다.**

`0812best.engine`(TensorRT)은 PC 에서 쓸 수 없다. 엔진은 특정 GPU + TensorRT
버전(Jetson 것)으로 직렬화되어 있다. `.onnx` 가 이식 가능한 산출물이다.

`cv2.dnn` 으로 측정한 모델 형상(추정이 아니라 실측):

```
입력   640x640 고정   ← 320/416/640x480 전부 model.24 Reshape 에서 실패
출력   1x25200x6      25200 = (80^2+40^2+20^2)x3,  6 = [cx,cy,w,h,obj,cls0]
클래스 1개 "astro-drone"
추론   CPU 30~42 ms (8 infer/s, 카메라가 ~8 fps 라 충분)
```

전처리는 `YOLO_MODEL/cpp/trt_engine.cpp` 를 읽고 실기와 동일하게 맞췄다 —
`letterbox()` + `copyMakeBorder(..., Scalar(114,114,114))` + RGB + `/255.0`,
카메라 해상도도 640x480 으로 동일.

### 관찰 2 — 타겟이 학습 대상과 달랐다

처음에는 `target_basket`(빨강, 8배)으로 시도했다. 가중치의 클래스가
`astro-drone` 하나뿐이라 드론 모양 타겟(`target_drone`, 정적 6배 iris)도 만들어
시험했다. 결과는 **미탐지**였다.

결정적이었던 것은 점수가 아니라 **박스 위치**였다. 전처리를 여러 조합으로 바꾸면
점수가 0.8~0.95 까지 올라갔지만, 박스 중심은 항상 원본 기준 `(585, 22)` —
화면 오른쪽 위 모서리, **기체 자신의 스탠드오프**였다. 타겟이 있는 `(314, 370)`
에서는 어떤 조합에서도 0.016 을 넘지 못했다.

점수만 보고 판단했으면 잘못된 결론을 낼 뻔했다. 이 모델은 프레임에서 자기
구조물에 가장 강하게 반응한다. 실기에서도 같은 위험이 있다.

이후 사용자가 실제 탐지 대상이 **흰색 바구니**임을 알려주었고, astrohome
(`192.168.0.116`) 의 `~/gazebo_yolo_bridge_0815/WHITE_BASKET_SETUP.md` 에 이미
정리된 해법이 있었다 — **학습셋에서 잘라낸 실사 텍스처를 평면에 입히는 것**.
도메인 갭이 사라지므로 모델이 학습 때 본 것과 같은 외형이 된다.

### 관찰 3 — 초점거리가 2.58배 어긋나 있다

`setting/MAVLink.yaml` 의 `pixel_focal_length_px: 530` 인데, 이 월드 `down_camera`
의 실측값은 **205.47 px** 이다.

직접 교차검증했다. 타겟을 북 8m 에 두고 기체를 북 10.1774m / 고도 4.0499m 에
세웠을 때 타겟이 화면 중심에서 130px 아래에 찍혔다.

```
130 px / 2.177 m = 59.7 px/m
fx = 59.7 x (4.0499 - 0.66) = 202.4 px      (문서값 205.47 대비 오차 1.5%)
```

`pos_calculator.cpp` 는 `ground_offset_m = pixel_offset / fx x altitude_m` 이므로,
`fx` 를 2.58배 크게 잡으면 **수평 거리를 2.58배 작게 본다.** 3차원 사선 분해에서
전진 성분만 과소평가되어 기체가 거의 수직으로 내려온다.

`MAVLink.yaml` 주석 자체가 이 값을 *"rough starting value, not derived from a
measured focal length/FOV"* 라고 적어두고 있고, `Document/algorithm.md` 도 미검증
임시값으로 명시해 두었다. 이번에 그 **구체적 결과**가 처음 드러났다.

다만 하강 전 구간에서 재보니 갈렸다 (0812best.onnx, conf 0.25, 640x480):

| 고도 | 1.033 x 0.690 | 3.10 x 2.07 |
|---:|---:|---:|
| 4.0 m | 0.777 | **0.959** |
| 3.0 m | 0.838 | 0.910 |
| 2.0 m | 0.907 | 0.323 |
| 1.5 m | 0.879 | 0.334 |
| 1.2 m | 0.733 | **미탐지 (0.011)** |

문서의 재현 조건은 "고도 약 4m" 고정이고 거기서는 `3.10` 이 최고다(박스

**기본값은 `model.sdf` 원본 그대로 `1.033 x 0.690` 으로 둔다.** 고정고도 진단이

### 통과하지 못한 것

착륙이 설계상 종료("1m 정지 → 5초 호버 → 착륙")가 아니라
`[EMERGENCY] 타겟 로스트 10.00s - LAND` 였다. `STOPPED` 상태에 한 번도 들어가지
못했다.

`target_distance.log` 의 픽셀값이 원인을 그대로 보여준다.

| 고도 | y_px | 기록 ground | 실제 ground | 오프셋/고도 |
|---:|---:|---:|---:|---:|
| 3.98 m | 200.0 | 1.50 m | 3.88 m | 0.97 |
| 3.53 m | 114.9 | 0.77 m | 1.97 m | 0.56 |
| 2.25 m | 143.9 | 0.61 m | 1.58 m | 0.70 |
| 1.38 m | 190.6 | 0.50 m | 1.28 m | **0.93** |

사선 이동이면 오프셋/고도 비가 일정해야 하는데 0.56 → 0.93 으로 **커졌다.**
`y_px` 도 114 → 190 으로 커져 타겟이 화면 위쪽 끝으로 밀려났고, 그래서 탐지율이
26% 로 떨어졌다. 고도 1.38m 에서 지상 반폭이 1.74m 인데 타겟이 1.28m 옆에
있었으니 프레임 경계에서 잘렸다.

### 왜 04:15 테스트는 성공했는가

`Document/logs/gazeboSim(08150415)` 는 `1m 정지 5.00초 호버링 완료 - 착륙` 으로
정상 종료했다. 그 로그를 보면 이유가 분명하다.

```
t= 3.03s  dist=3.69m  alt=3.67m   vx=0.01  vz=0.25
t=12.12s  dist=2.39m  alt=2.37m   vx=0.02  vz=0.12
t=39.38s  dist=0.90m  alt=0.87m   vx=0.00  vz=0.00  ← STOPPED
```

`dist` 와 `alt` 가 거의 같다. 수평 거리가 `sqrt(3.69^2 - 3.67^2) = 0.39 m` 뿐,
즉 **기체가 처음부터 타겟 거의 바로 위에 있었다.** 수평 성분이 0 에 가까우니
초점거리 오차가 드러날 여지가 없었고, 타겟도 화면 중앙에 머물러 LOST 가 0건이었다.

`algorithm.md` 3-1 의 설계는 "AUTO 로 날다가 타겟 확정 즉시 가로채기" 이므로
가로채는 순간에는 항상 수평 거리가 크다. **04:15 는 그 구간을 검증하지 않았다.**

참고로 `Document/logs/gazeboSim_log(08150320)` 은 로그 줄에 `vz` 필드 자체가 없고
고도가 4.00m 에서 움직이지 않는다 — 수직 성분 구현 이전 바이너리이며,
`algorithm.md` 가 인용한 실패 사례가 이것이다.

## 남은 문제

1. **`pixel_focal_length_px` 실측 반영.** 시뮬용으로 `SIM_FX=205.47` 옵션을
   `run_sim_demo.sh` 에 넣어 두었으나 **기본은 꺼져 있다** — 실비행 캘리브레이션
   값이라 임의로 바꾸지 않았다. 켜면 종료 시 `setting/MAVLink.yaml` 과
   `gazeboSim/MAVLink.yaml.sim-backup` 양쪽을 530 으로 원복한다.
   실기 IMX219 의 초점거리는 여전히 미검증이다.
2. **하향 카메라에 기체 자기 구조물이 찍힌다.** 모델이 여기에 강하게 반응한다
   (측정 0.10~0.87). 자기 구조물은 매 프레임 같은 자리에 있어 5프레임 스트릭이
   오히려 안정적으로 통과시킨다. `algorithm.md` 가 계획한 ROI 크롭이 이 문제를
   푸는 장치다.
3. **검출기가 스트림 단절 후에도 `found:true` 를 유지한다.** Gazebo 를 내린 뒤
   `age_ms` 가 4.9시간인데도 참이었다. `sim_mission_core.py` 표시에는 신선도
   게이트(2초)를 넣었으나, 검출기 자체는 그대로다. 소비자인
   `target_distance.cpp` 가 `age_ms` 를 보므로 제어에는 영향 없음.
